## Decisions

1. Source files were at the repo root, not in `/source`. Moved them into `/source` with `git mv` to match the brief.
2. The rule list arrived as a `.docx` (`100-fictional-underwriting-decline-rules.docx`), not Markdown. `scripts/parse-rules.ts` reads the `.docx` with `mammoth` (raw text) and parses the same `DR-xxx Submitting Insurer: ... Rule Category: ...` pattern.
3. The "key principles" image was not in the repo. The four principles (human-in-the-loop, transparency, consistency, consumer protection) are taken from the brief text.

4. Stack: Vite 8, React 19, TypeScript 5.9 (pinned; npm offered 7.0 which is the new native compiler and was avoided for stability), Tailwind 4, Zustand 5, recharts 3, zod 4, vitest 5.
5. Citation registry keeps a `sectionToConfirm` field for the human checker. It is never rendered as a citation in the app; the app shows instrument plus "section not verified".
6. Framework-deck references (slides 3-12) are marked `verified: true` because they were checked against the supplied PDF, which is their source.
7. Issue code taxonomy has 25 codes: the 21 from the brief plus `PROHIBITED_FACTOR` (credit information, coverage lapses, administrative lapses), `LESS_RESTRICTIVE_ALTERNATIVE` (rating or an endorsement would do), `SUBJECTIVE_JUDGMENT` (Level 3 "is it subjective") and `PRIVACY_INTRUSION` (social media, child protection records).
8. Level 1 "Already exists in the market" status meaning: pass = approved precedent with same or similar intent; insufficient information (low) = no precedent, assessed on its own merits; concern = closest match is an illustrative non-compliant example. Level 1 does not add to the score; it is a gate.
9. "Material" insufficient information = an `insufficient_information` finding at Levels 2-4 with medium or high severity. This is how the AI signals that the gap could change the outcome; scoring then routes to Request more information.
10. Level 4 status maps to the framework's yes / no / maybe: pass = "No (nothing inappropriate)", concern or insufficient = "Maybe", fail = "Yes (conflicts with public policy)".
11. Similarity = 0.65 x TF-IDF cosine on rule text + 0.35 x feature overlap (categories 0.35, trigger types 0.45, threshold 0.1, lookback 0.1). Top 5 per rule, with the best precedent forced into the list if none made the top 5.
12. Precedents: 14 approved rules (AP-01 to AP-14) from slide 12 with invented insurers from a separate name set and illustrative approval years 2015-2023; 6 framework common examples (FX-01 to FX-06, slide 3); 5 illustrative non-compliant examples (NC-01 to NC-05, slide 5).
13. Added a fifth decision option, "Route to eligibility-rule process", used only when the AI recommendation is Out of scope.
14. Scoring calibration (once): 15 weight/threshold configurations all matched the 13 anchors, so the starting values (40/35/25; 75/50) were kept and frozen. See prompt-log entry 7.
15. Findings are authored in compact form (`data/authoring/batch-*.ts`) and expanded mechanically; `common.ts` holds standard wording for recurring findings.
16. Rule 17 (actuarial severity) clarified during batch 07 so administrative rules whose basis is legal are not automatically routed to Request more information. Logged as prompt-log entry 8; no earlier finding changed.
17. Consistency-audit changes are applied as explicit patches (`data/authoring/audit-fixes.ts`) and recorded per assessment in `auditNotes`, shown in the app.
18. Scoring outcomes were never tuned by editing findings to hit an expected answer (DR-071, DR-085 left as scored; listed in spot-check as override candidates).
19. Sample filings are generated by `scripts/make-samples.ts` (docx npm; the PDF is converted with LibreOffice). `libreoffice-writer` was installed in the build container for this and for the report PDF.
20. PDF parsing uses the `pdfjs-dist` legacy build. The modern build calls `Map.prototype.getOrInsertComputed`, which current Chromium does not ship; the end-to-end test caught this. The legacy build bundles the polyfill.
21. The audit trail stores raw keys (for export and traceability) but displays plain-English labels for decisions, recommendations, reason codes, triggers and statuses. Issue codes and criterion keys stay as codes because the product shows them as codes everywhere.
22. Playwright uses the pre-installed Chromium (`/opt/pw-browsers/chromium`) and serves the production build with `vite preview --base /simrule/`, the same path as GitHub Pages.
23. The built site in `/docs` is committed (no GitHub Actions). It uses relative asset paths and hash routing, so it works under `/simrule/` on GitHub Pages; verified by serving `/docs` at `/simrule/` from a plain static server with no console errors and a working PDF upload.
24. Stretch done: optional live AI assessment for uploaded rules (`src/lib/liveAssessment.ts`, `src/lib/liveClient.ts`). Off by default; the visitor's API key lives only in the component's memory and is dropped on success or navigation. Uses the official Anthropic TypeScript SDK in browser mode (it sends the `anthropic-dangerous-direct-browser-access` header), loaded lazily as a separate chunk. Current Opus model id confirmed from the API reference at build time; effort `high`; server-side refusal fallback enabled (`fallbacks: "default"`). Structured outputs with enums restrict criteria, issue codes, citations and precedent ids; non-verbatim quotes are dropped; sentence-count problems are shown as warnings; structural errors reject the run. Never tested against the live API (no key in the build environment); tested against a mocked API end to end.

25. Architecture diagram is generated by `scripts/make-architecture.ts` from explicit coordinates (a hand-laid layout, not auto-layout) so the SVG, PNG (resvg, system Liberation Sans) and PDF (Chromium, US Letter landscape) always match; the script fails on any text overflow. Minimum text size 17 units on an 11 x 8.5 in page at 150 units per inch, about 8 pt printed. Two connectors (decision notice to the insurer, registry back to similarity) were replaced by text references because they crossed other arrows.
26. The optional chatbot (Chatbase) and avatar video (HeyGen) were skipped by the author after merge: the free Chatbase plan allows no further agents, and a video was not wanted in a public repository. Their drafted packs were removed. The chatbot stays in the architecture diagram as a planned production component marked "Not built".
27. Report built by `scripts/make-report.ts` (docx package, Arial so Word and LibreOffice paginate alike; PDF via LibreOffice). The reflection and the AI-use disclosure's last sentence were drafted with yellow highlights for the author to rewrite; the author's rewrites are now in the script as plain text, with one typo fixed ("a add-on" to "an add-on").
28. Report author Kazumi Li; report date October 7, 2026 (date of the final version).
29. Deliverables reorganised: `deliverables/report/` holds only the report, `deliverables/process/` holds the prompt log, consistency audit, spot check and VERIFY list, `deliverables/demo/` holds the recording script, samples, screenshots and accessibility report. The chatbot slot (`src/config/integrations.ts`, the widget component and its header and How it works links) was removed from the app.

## Open issues

1. **Fetch blocked.** The environment's network egress policy blocks `www.ontario.ca`, `www.fsrao.ca` and `www.ohrc.on.ca` (WebFetch returns EGRESS_BLOCKED). No citation could be verified against the official source, so every entry in `knowledge/citations.json` has `verified: false` and `section: null`. Web search result snippets were used only for orientation and are never presented as verified. Full list in `deliverables/process/VERIFY.md`.

2. **Live assessment not run against the real API.** No API key exists in the build environment (by design). The browser call is tested end to end against a mocked API only.
3. **No chatbot or avatar video.** Both optional components were skipped by the author (see Decision 26).
4. **Personal reflection** is in the author's own words; check the final wording before submission.
